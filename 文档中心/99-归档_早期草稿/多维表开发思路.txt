先给核心结论
理论上可以模拟出视觉上近似飞书多维表的卡片视图、画册视图，但存在原生能力天花板，分为两条实现路线：原生连续窗体 / ActiveX 自定义控件；二者体验和限制差异很大。
先对齐概念：
卡片视图（看板）：任务卡片，常按状态分组、横向排布、可拖拽；
画册视图：大图优先，多列网格卡片，图片 + 少量摘要信息。
路线 1：Access 原生能力（不依赖第三方 ActiveX 控件，最稳妥）
核心载体：连续窗体（多项目窗体）
主体节绘制一张「卡片模板」：图片控件、文本标签、边框、背景色、操作按钮；窗体默认视图设为【连续窗体】。
✅ 能做到：
单条记录渲染成独立卡片；
支持图片展示（画册视图基础）、卡片底色区分状态；
卡片内放置编辑控件、详情按钮；
配合窗体页眉筛选框、VBA 刷新数据源，切换不同数据集；
完全脱离外部控件，分发数据库不会出现控件缺失报错。
❌ 原生硬限制（无法绕过）
只能垂直自上而下排列卡片，不支持自动多列网格布局
原生连续窗体没有 “自动换行多列”。窗口拉宽，卡片依旧单列向下滚动；
飞书画册是自适应网格（一行 N 张卡片，自动换行），Access 原生做不出。
想要多列网格，只能两种折中方案：
① 手工做多组并列子窗体，预先均分列，窗口缩放会错乱；
② 嵌入 WebBrowser，用 HTML+CSS 渲染卡片（属于混合方案，不再是纯 Access 窗体）。
不支持卡片拖拽排序、拖拽分组（看板核心交互）
飞书看板可以把卡片拖到不同状态分组；原生连续窗体没有拖拽交互。
滚动性能上限低
记录量大（几百条以上、大量图片）时，连续窗体频繁重绘，容易卡顿、图片闪烁。
简单说：原生连续窗体可以做出纵向单列卡片列表，近似简易卡片视图；无法原生实现画册多列网格、看板拖拽分组。
连续窗体纵向卡片效果
路线 2：ActiveX 自定义控件（你提到的自定义控件方案）
可选控件：Microsoft ListView Control 6.0 / 第三方 Gallery / 卡片 ActiveX 控件
ListView 控件重点说明
ListView 内置 4 种模式：报表视图、大图标、小图标、列表视图。
大图标视图：非常接近画册视图，图片 + 标题；
可以加载图片列表，VBA 循环填入记录；
✅ 优势：
原生支持多行多列网格排布，完美匹配画册视图布局；
支持图标 / 缩略图批量展示；
可以捕获点击事件，打开详情弹窗；
❌ 致命短板（工程落地重点）
控件无绑定数据源
不像连续窗体直接绑定表 / 查询；全部需要 VBA 循环读取记录、逐行 AddItem 加载。新增、修改数据后必须手动刷新列表，无法双向实时联动（飞书视图修改立刻同步底层数据）。
单元格 / 项目内部不能自由放置复杂控件
ListView 条目只能放图片 + 文字，不能在卡片内部自由摆放多个文本框、按钮、复选框。
飞书卡片内可以自由排布各类字段；ListView 卡片是极简模式，很难实现丰富卡片内容。
分发兼容性大坑
ListView 6.0 属于旧版 MSCOMCTL.ocx，64 位 Office 经常缺失、注册失败；客户电脑极易出现 “控件无法加载、显示灰色占位框”。
第三方商业 ActiveX 控件还涉及授权、部署注册难题。
额外备选混合方案：WebBrowser 控件
窗体嵌入 WebBrowser，用 HTML+CSS 渲染卡片网格（画册 / 看板），JS 和 VBA 互相通信读写 Access 表。
👉 视觉效果最接近飞书多维表视图，但开发量巨大，属于 “Access 外壳套网页”，已经脱离纯 Access 窗体开发范畴。

能不能用自定义控件模拟卡片、画册视图？

可以独立开发本地多维表软件
完全可行，核心思想和你之前理解一致：一份原始表格数据，额外保存多套「视图配置」，不同视图组件读取同一份源数据，仅改变渲染展示方式；编辑操作回写到原始本地文件。
关键点区分：
原始业务数据：来自本地 xlsx/csv（你的源表格）
视图元配置：看板分组条件、筛选规则、卡片布局、甘特起止字段、日历绑定日期字段，不属于原始 Excel，需要软件自己保存
视图层：表格 / 看板 / 画册 (画廊)/ 日历 / 甘特 / 表单，只是 UI 渲染器，不复制业务数据
两种产品形态
形态 1：桌面独立 exe 软件（完全本地，无网络）
底层存储选型二选一
直接读写 xlsx/csv 作为主数据源
原始数据就是用户的 Excel 文件；视图配置单独存为附属配置文件（.view.json），不和原始 Excel 混在一起。
✅优点：用户可以继续用 Excel 打开修改源文件；软件只负责多视图浏览编辑；编辑后直接写回 xlsx/csv。
⚠️短板：Excel 本身不支持多维表的跨表关联、公式字段，只能做普通平面表格的多视图；复杂关联字段很难回写进普通 xlsx。
内部 SQLite 作为主库，可导入导出 xlsx/csv
软件内部用 SQLite 保存完整多维表（多表关联、特殊字段、全部视图配置），提供导入 xlsx、导出 xlsx 能力。
✅优点：完整复刻飞书多维表全部能力：看板拖拽改状态、甘特拖拽改时间、画廊画册卡片、表单录入、跨表关联；没有云端依赖，全部本地文件。
⚠️短板：原始数据保存在软件私有.db文件，Excel 只是导入导出载体，不能直接拿 Excel 作为日常主文件GitHub。
你想要的：基于本地表格数据文件进行各种视图查看、编辑操作
如果坚持以 xlsx/csv 为权威源文件，只能实现「平面数据表」的多视图；多维表真正的多表关联能力，普通 Excel 文件承载不了。
形态 2：Electron 套前端开源多维表组件打包成本地 exe
已有开源组件可以直接复用：Smart‑Table、Pxcharts、NocoDB 前端组件，打包成桌面程序，本地读写文件，不需要后端服务。
支持全部 6 类视图：表格、表单、看板、画廊 (画册)、日历、甘特，xlsx/csv 导入导出，视图配置持久化本地磁盘。

核心技术难点（做本地多维表软件必须解决）
视图配置与原始数据分离
源 Excel 不动，视图的筛选、分组、卡片布局、列显示隐藏存储在独立配置，切换视图不修改原始数据。
双向编辑同步
在看板拖拽卡片修改状态、甘特拖动进度条修改日期，修改必须写回底层源数据（xlsx 或者 SQLite），所有其他视图立刻刷新。
xlsx 的局限性
普通 Excel 没有 “视图” 概念，没有字段元信息（字段类型、选项列表）。如果直接以 xlsx 作为权威数据源，不支持多选、关联表、rollup 汇总字段，只能做简单文本、数字、日期。
大性能
几千‑几万行，画廊画册大量图片卡片渲染、虚拟滚动；如果直接解析 xlsx，大文件加载会卡顿。
两种开发路线建议
路线 A：轻量化，以 xlsx/csv 为权威源（满足你 “基于本地表格文件”）

保存：业务数据只写回这个 xlsx；视图配置保存同目录下xxx.view.json
能力：表格视图、看板（按某列分组）、画册画廊卡片、日历视图、简易甘特；不支持跨表关联高级多维能力
适合：只是给普通表格增加多视图浏览编辑，不做复杂关系数据库。
路线 B：完整多维表能力（对标飞书多维表本地版）
主存储：SQLite 本地文件（私有格式）
交互：完整看板拖拽、画廊画册、甘特、日历、表单、跨表关联、公式字段
兼容：提供导入 xlsx/csv，导出 xlsx/csv 功能；Excel 只是交换载体，不是日常主文件。

NocoDB：把 SQLite 变成多维表 UI，网格 / 看板 / 画廊 / 日历视图齐全，适合本地部署，可打包桌面版。

本地多维表工具开发文档（基于 VSTO 方案）
文档概述
项目目标
基于现有 VSTO (Excel 插件)，开发本地多维表扩展工具：以 Excel 工作簿作为权威数据源，实现多视图能力：表格视图、表单视图、看板视图、画册 (画廊) 视图、日历视图、简易甘特视图；视图配置独立存储，编辑操作回写 Excel 单元格 / 表格，不破坏原有 Excel 数据；全部本地运行，无云端依赖。
核心模型：业务数据驻留在 Excel 表；视图元数据独立存储；UI 视图仅做渲染，修改双向同步回 Excel 源数据。
边界约束：Excel 本身是平面表格，无法原生支持飞书多维表的跨表关联、查找引用、汇总字段，本 VSTO 方案只做单表多视图，不实现多表关系。
适用范围
宿主：Microsoft Excel，VSTO‑Add‑in（.NET Framework /.NET 6‑8 VSTO）
数据源：Excel ListObject（超级表）作为唯一业务数据源
输出：多视图窗口 / 任务面板，视图配置持久化，数据编辑双向回写 Excel
一、核心技术点
1. 数据层设计
1.1 业务数据源
使用 Excel ListObject（结构化超级表）作为业务主存储，所有业务行数据真实保存在 Excel 工作表。
约束：必须使用超级表，禁止使用普通 Range，方便增删行、列识别。
1.2 视图元数据存储（关键）
Excel 单元格无法存储复杂 JSON 视图配置，提供两套持久化方案：
工作簿自定义 XML 部件（推荐 VSTO 原生）
将视图配置 JSON 序列化，写入 Excel OpenXML 自定义部件，嵌入当前 xlsx 文件内部。
优势：视图配置跟着文件走，发送文件视图配置一起携带；不污染工作表单元格。
劣势：WPS 打开会丢失自定义 XML 部件；仅 MS Excel 生效。
外部附属配置文件
同目录下生成 {文件名}.multiview.config.json，业务在 Excel，视图配置在外置 json。
优势：WPS 也可读取；文件损坏配置可备份。
劣势：需要两个文件一起分发，容易丢失配置文件。
视图配置 JSON 核心字段示例
json
{
  "Views":[
    {
      "ViewId":"view_kanban_01",
      "ViewType":"Kanban", // Table/Form/Kanban/Gallery/Calendar/Gantt
      "ViewName":"任务看板",
      "SourceTableName":"Table1",
      "Filter":"[状态]='进行中'",
      "GroupByColumn":"状态",
      "VisibleColumns":["任务名称","负责人","截止日期"],
      "CardLayout":{"TitleField":"任务名称","ImageField":"附件图片","DescFields":["负责人","截止日期"]},
      "Sort":[ {"Field":"截止日期","Order":"asc"} ]
    }
  ]
}

1.3 数据读写层（VSTO C#）
读：读取ListObject行，映射为内存实体集合；应用视图配置（过滤、分组、排序）得到视图数据集。
写：视图界面修改（卡片编辑、看板拖拽修改分组字段、日历修改日期），回写到 ListObject 对应行单元格，触发 Excel 原生事件刷新工作表。
重要：禁止内存副本脱离 Excel 源；所有修改必须落地 Excel。
2. UI 视图层（VSTO 两种 UI 实现路线）
VSTO 本身没有现成的看板、画廊、甘特控件，全部需要自己组合。
方案 A：Custom TaskPane + WinForms/WPF（主流 VSTO 方案）
TaskPane 停靠在 Excel 侧边；内部承载 WPF UserControl 做全部多维表视图。
Table 视图：DataGrid
Form 表单视图：动态生成输入控件，根据超级表列类型生成文本框 / 日期选择器 / 下拉框
Kanban 看板视图：ItemsControl 分组布局，模拟看板列；拖拽用MouseDrag实现卡片移动
Gallery 画册视图：WrapPanel 卡片流式布局，图片优先展示，次要字段作为卡片简介
Calendar 日历视图：自定义日历面板，按日期字段把行渲染到日历格子
Gantt 甘特视图：简易进度条，绘制时间轴；拖拽修改起止日期回写 Excel
痛点：WPF 做复杂拖拽、虚拟滚动、大量卡片渲染，需要自行实现虚拟化，上万行性能压力大。
方案 B：TaskPane 嵌入 WebView2（推荐优先选择）
TaskPane 内部放置 WebView2 控件，前端用 Vue/React 实现全部 6 套视图；C# 做桥接层。
C# 侧：读取 Excel ListObject 数据，序列化为 JSON 传给 WebView2；接收前端编辑指令写回 Excel。
前端：复用开源多维表 UI 组件，实现看板、画廊、日历、甘特，拖拽交互成熟。
优势：视图组件不用从零造轮子；UI 体验对标飞书多维表。
劣势：打包分发依赖 WebView2 运行时。
3. 关键业务逻辑
视图切换：同一套内存业务数据，加载不同 View 配置对象，UI 重新渲染，不改动 Excel 源。
双向同步机制
Excel 手动修改单元格 → VSTO 监听Worksheet_Change事件，通知 UI 视图刷新。
UI 视图编辑 / 拖拽 → C# 层写入 ListObject 单元格，触发 Excel 原生变更。
筛选、排序、分组逻辑：内存中对实体集合做 LINQ 处理，不修改 Excel 工作表本身的筛选器（视图层筛选，不改动原始表格）。
行新增删除：UI 新增行，调用ListObject.ListRows.Add()写入 Excel；删除行直接删除 ListRow。
4. 性能关键点
行数 > 3000 行，WPF 原生控件不做虚拟滚动会 UI 卡死；WebView2 前端虚拟列表是更优解。
不要频繁循环读写 Excel 单元格，批量读取 Range 到内存数组，修改完成批量回写。
屏蔽 Excel 屏幕更新 Application.ScreenUpdating = false，批量操作后恢复。
视图配置读取做内存缓存，打开文件只解析一次 XML/json。
5. 局限性（VSTO+Excel 架构固有，无法规避）
仅支持单表，无法实现飞书多维表跨表关联、lookup、rollup；Excel 是平面表。
图片存储：Excel 单元格不能原生存图片字段；图片只能存本地路径，卡片视图加载本地图片。
WPS 兼容：VSTO 插件不能在 WPS 运行；自定义 XML 部件 WPS 打开会丢失视图配置。
没有多用户并发，本地单用户编辑。

1 整体架构总览
plaintext
独立桌面应用
├── 文件解析层：读取/保存 xlsx / csv
├── 核心业务层
│   ├── 原始数据集：内存中的表格数据（来源于xlsx/csv）
│   ├── 视图配置管理器：加载/保存多套视图配置
│   ├── 视图引擎ViewEngine：原始数据 + 视图配置 → 输出过滤、分组、排序后的视图数据集

├── UI渲染层（6套视图）
│   ├── 表格视图 Table
│   ├── 表单视图 Form（单条记录编辑窗体）

核心原则：
源 xlsx/csv 是权威数据源；视图配置不和业务数据混在一起，存在外置 json。
UI 所有视图只做渲染，修改全部落地回源文件；切换视图不改动原始数据。
打开文件时：读取 xlsx 到内存；读取同目录下配套.multiview.json视图配置；关闭 / 保存时写回 xlsx，写回配置文件。
视图配置文件 xxx.multiview.json 核心结构
json
{
  "SourceFile":"data.xlsx",
  "SourceSheet":"Sheet1",
  "PrimaryKey":"_rowIndex",
  "Views":[
    {
      "ViewId":"v001",
      "ViewType":"Kanban",
      "ViewName":"任务看板",
      "FilterExpr":"[状态]!=''",
      "GroupBy":"状态",
      "Sort":[{"Field":"截止日期","Order":"asc"}],
      "VisibleFields":["任务名称","负责人","截止日期"],
      "CardMeta":{"Title":"任务名称","Image":"图片路径","Desc":["负责人","截止日期"]}
    }
  ]
}

PrimaryKey：因为普通 xlsx 没有主键，内部用行号作为临时主键；新增行后内存维护行标识。
配置文件和 xlsx 放在同一个文件夹；如果用户复制 xlsx，需要连带复制该 json，否则视图配置丢失。

3 核心技术点详解
3.1 文件解析层关键点
Xlsx 读写使用 EPPlus (NET) /exceljs (Node)，不调用 Excel COM。
将工作表转为内存表格模型：List<Dictionary<string,object>>，每一行是一条记录，key 为列名。
注意：普通 Excel 没有主键，内部使用行索引作为临时主键；新增行时内存维护 ID 映射。
保存逻辑：内存数据集完整写回 xlsx；不要增量改写单元格，避免格式错乱。
csv 需要处理编码（GBK/UTF‑8），分隔符自动识别。
风险：Excel 原有的部分格式、条件格式、宏，第三方库读写会丢失；本软件定位是数据查看编辑工具，不完整保留 Excel 复杂样式。
3.2 视图引擎 ViewEngine（核心模块，与 UI 无关）
输入：
原始全量数据集
单个视图配置对象（Filter、GroupBy、Sort、VisibleFields）
输出：经过过滤 → 排序 → 分组之后的视图数据集，供给 UI 渲染。
重要：过滤、分组、排序全部在内存完成，不修改磁盘上的 xlsx 源文件；视图只是展示变换。
3.3 双向数据同步机制
用户在 UI（看板 / 画册 / 表单）修改某一条记录字段值
修改写入内存原始数据集
触发保存：将内存数据集完整序列化写回 xlsx 磁盘文件，同时更新.multiview.json视图配置。
切换其他视图：全部基于同一份内存原始数据集重新执行 ViewEngine 渲染。
注意：不要只改 UI 副本；内存必须维护唯一权威数据集。
3.4 六大视图实现要点
表格视图 Table
虚拟滚动表格组件；支持列隐藏、排序。
表单视图 Form
根据字段类型动态生成输入控件：文本框、数字输入、日期选择、下拉选择。用于单条记录弹窗编辑。
看板视图 Kanban
按 GroupBy 字段分组，生成多列；卡片拖拽跨列，拖拽完成修改对应记录字段值，回写内存数据集。
画册视图 Gallery
流式 Wrap 卡片布局；优先展示图片（存储本地文件路径），次要字段作为卡片简介；需要虚拟化，否则上千张卡片渲染卡死。
日历视图 Calendar
绑定一个日期字段，把记录渲染到日历对应日期格子。
甘特视图 Gantt
绑定开始日期、结束日期字段，绘制横向进度条；拖拽条修改起止时间，回写数据。
3.5 视图配置持久化
配置文件命名规则：{源文件名}.multiview.json，和 xlsx 同目录。
当用户复制、重命名 xlsx 文件，软件需要同步提示处理配置文件，否则视图配置丢失。
备选增强：可以把配置嵌入 xlsx 的 OpenXML 自定义部件；但第三方工具编辑 xlsx 容易丢失自定义部件，所以外置 json 更稳妥。
3.6 性能约束
行数 1 万行以上：必须开启虚拟列表 / 虚拟卡片，只渲染可视区域；否则 UI 卡顿。
xlsx 读写不要频繁保存；设置手动保存按钮 + 可选自动保存防抖。
图片字段：不把图片嵌入 xlsx，只保存本地绝对 / 相对路径；软件根据路径加载图片。
