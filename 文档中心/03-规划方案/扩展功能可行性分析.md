# 多维表分析软件 — 四项功能扩展可行性分析

> 分析基准：当前工程（Excel-DNA 1.9 + .NET 8 + WebView2 SPA `index.html` 为真实 UI，C# `HtmlMainForm.cs` 为宿主与 `api.call` 数据桥）。
> 本文在用户原始描述基础上，对部分含糊点做了细化/纠偏，并在「细化说明」中标注。
> **（2026-08-16 修订：补充 ①基础视图不可删除 + 右键菜单管理 ②HTML 图表采用「模块化五层分离」结构（参考 `大屏结构说明.md`）③Ctrl+滚轮缩放控制可行性）**

## 0. 总体结论与建议优先级

| 功能 | 实现难度 | 估时(人日) | 业务价值 | 建议 |
|------|----------|-------------|----------|------|
| ① 画册图片圆形显示 | **低** | 0.5–1 | 中（人员照片类场景） | 优先做（快赢） |
| ③ 视图另存为新视图 | **中** | 2–3 | 高（数据管理方法复用） | 第二顺位 |
| ② 甘特拖拽调整/移动 + 保存模式 | **中高** | 3–5 | 高（防误改 + 灵活编辑） | 第三顺位（核心难点在关闭拦截） |
| ④ HTML 图表视图 | **中** | 3–4 | 高（图表扩展性） | 最后做（架构增量最大） |

**推荐落地顺序**：① → ③ → ② → ④。①②④ 三者相互独立、可并行；② 的"保存模式"与 ③ 的"视图配置持久化"共享 `saveConfig()`/`APP_SETTINGS` 通道，建议 ③ 先沉淀通用"视图管理"能力，② 复用之。

## 1. 现有架构基础（确保分析可落地）

为便于评估，先盘点与四项功能直接相关的**已存在能力**（均位于 `MultiTableAddin/src/MultiTableAddin/Html/index.html`）：

- **真实 UI 载体**：`HtmlMainForm.cs` 启动 WebView2 加载内嵌 `index.html` 单页应用；所有视图（表格/表单/看板/画册/日历/甘特/仪表盘/图表）均在此 SPA 内渲染。C# 侧通过 `api.call(name, pars)` 分发数据读写（`updateCell` 写回 Excel/WPS 超级表，`getImageBase64` 读图片等）。
- **配置持久化**：`saveConfig()` 将当前 `cfg`（含 `views[]`、各视图 config、`cardMeta` 等）序列化到 `multiview.json`；`saveAppSettings()` 持久化 `APP_SETTINGS`（`index.html:531` 定义：`topMost / openMaximized / dashTheme / labelHideThreshold / monthMaxEvents / weekStartDay / calDefaultDurationMinutes / showChartCardTools`）。
- **画册配置**：`cfg.cardMeta = { title, image, imageFolder, imageMatchField, colorField, description }`（渲染见 `renderGalleryInner`，约 1836 行；设置面板见 3243 行起）。图片经 `setImgSrc`→`getImageBase64` 以 base64 显示。
- **甘特拖拽（关键）**：`makeGanttBarDraggable(bar, r, cfg, dim)`（`index.html:2718`）**已实现**鼠标拖拽，规则：
  - 拖条体左/右 8px 边缘 = `resize`（改宽度 → 改结束时间，时长变化）；
  - 拖条体其余区域 = `move`（改 left → 起止同步平移，**时长不变**）；
  - 增量按 `ganttState.min/max`（当前可见 range）换算为日期，**已天然跟随日/周/月/年缩放粒度**；日视图对齐 15 分钟、其它对齐到天（`alignDate`）。
  - **拖起释放即调用 `api.call('updateCell', …)` 即时写回数据**（`index.html:2771`）——这是"手动保存模式"要改写的现状。
- **日历拖拽**：`monthDragStart(ev, r, cfg, cell, mode)`（`index.html:2209`）同样支持 `move / resize-start / resize-end`，证明"平移保时长"逻辑在代码库已有成熟范式。
- **视图列表**：`state.views` / `cfg.views` 已是视图数组，`saveConfig()` 同步 `groupBy / cardMeta / calendarConfig / ganttConfig / chartConfig / dashboardConfig / visibleFields / summary` 等（`index.html:3804`）。视图切换栏 `renderViewbar()`（706 行）已存在"保存设置"按钮。
- **`dash.html`**：项目根目录已存在一份 ECharts 风格的"项目管理可视化看板"HTML demo（独立页面，非插件内嵌）。

> 结论：四项功能中，**① 几乎零基础设施新增**；**② 拖拽力学已就绪，缺的是"提交时机控制 + 关闭拦截"**；**③ 数据模型已就绪，缺的是"视图管理 UI + 当前态捕获"**；**④ 需要从零设计"模板视图 + 数据桥"，但 `dash.html` 可作样板**。

## 2. 功能一：画册视图图片显示模式（正常 / 圆形）

### 细化说明
- 原描述已清晰。建议将"显示模式"抽象为一个枚举：**`normal`（矩形直接显示，现状）/ `circle`（圆形居中裁剪，适合人员头像）**。
- 圆形实现本质 = 在固定正方形裁剪区内 `object-fit:cover` + `border-radius:50%`，即只保留圆内像素，圆外透明。

### 现状
- 图片渲染在 `.gimg`（固定 120px 高、`flex-shrink:0` 的卡片上半区），经 `setImgSrc` 注入 `img.src`。`cardMeta` 已持久化，新增一个字段即可随视图保存。

### 实现方案
1. **数据模型**：`cfg.cardMeta.imageShape = 'normal' | 'circle'`，默认值 `'normal'`；`saveConfig()` 自动持久化（无需改 C#）。
2. **渲染分支**（`renderGalleryInner` 图片块）：
   - `circle` 模式：把 `.gimg` 改为**正方形**（如 `width:120px;height:120px;margin:0 auto;border-radius:50%;overflow:hidden`），内部 `<img>` 维持 `object-fit:cover;width:100%;height:100%`。
   - `normal` 模式：保持现状矩形区。
3. **设置面板**：在画册"视图设置"（`showViewSettings`）的图片相关区域加一个下拉「图片形状：正常 / 圆形」，写入 `cardMeta.imageShape` 并 `saveConfig()`。
4. **选中/悬停态**：圆形模式下 `selected` 边框加粗即可，无需特殊处理。

### 影响范围
- 仅 `index.html` 的 CSS（`.gimg` 分支）+ 渲染函数 + 设置面板；不触及 C#。
- `verify-build.py` 需新增 `imageShape` / `border-radius:50%` 检查串。

### 难度与风险
- **难度：低（0.5–1 人日）**。纯前端 CSS + 一个配置字段。
- **风险**：① 圆形区与现有"卡片上半区 120px"高度需协调（圆形建议固定正方形，避免椭圆）；② 图片加载失败时的占位文字在圆形区内显示需对齐；③ 若后续要支持更多形状（圆角矩形等），应预留 `imageShape` 枚举而非写死样式。

### 验证点
- 切到圆形模式，人员照片应呈正圆且不变形；切回正常恢复矩形；重开插件后模式保持。

### 实现状态（2026-08-14，v2.9.18 / #400）
- ✅ **已实现并交付**。新增 `cardMeta.imageShape = 'normal' | 'circle'`，并在 C# `Models.cs` 的 `CardMeta` 增加 `ImageShape` 字段（保证反序列化不丢字段、随 `.multiview.json` 视图配置持久化）。
- 设置面板「图片显示模式」下拉：正常（矩形）/ 圆形（居中裁剪）；圆形采用 `104×104` 居中正方形 + `border-radius:50%` + `object-fit:cover`。
- 软件内「帮助」画册小节已补充该模式说明；`verify-build.py` 已加 #400 检查项。

## 3. 功能二：甘特视图拖拽调整/移动 + 可视化保存模式

### 细化说明（纠偏原描述）
- **"调整"** 与 **"移动"** 需明确区分，二者当前代码已分别存在：
  - **调整（resize）**：拖动条体边缘，改变**起或止时间点**，**项目占用时长随之变化**（适合修正工期）。
  - **移动（move）**：拖动条体主体，起止点**同步平移、时长不变**（与日历日视图纵向改时间同一逻辑）。
- 原描述"跟随右上角周/月视图切换"——甘特自身已有 day/week/month/year 缩放档（`ganttState` + 控制行 `gantt-ctrl-row`），`makeGanttBarDraggable` 已按当前 range 换算，**无需额外"跟随"逻辑**，缩放档本身就是粒度开关。日视图下幅度本就精细（15 分钟对齐），不会出现"幅度过大"；若出现，应检查是否误用了固定像素步长而非 range 百分比。
- **保存模式仅针对"数据值（时间/日期）的拖拽提交"**，与"视图布局配置（分组/筛选/字段）的保存"解耦——后者仍走现有 `saveConfig()` 即时持久化，不受自动/手动开关影响。这样避免把"误拖导致布局丢失"也纳入提示，范围更清晰。

### 现状
- 拖拽力学 80% 已就绪（见 §1）。**唯一现状缺口 = 提交即时性**：拖完立刻 `updateCell` 写回，没有"缓冲/确认"环节。

### 实现方案
**3.1 拖拽调整/移动（基本复用，小修）**
- 保持 `makeGanttBarDraggable` 的 `move/resize` 判定；确认日/周/月/年各档的 `alignDate` 对齐粒度符合预期（日=15 分，其余=天）。
- 日历侧同理已具备，无需改。

**3.2 保存模式开关（软件设置）**
- `APP_SETTINGS` 增加 `visualSaveMode: 'auto' | 'manual'`（默认 `'auto'`，兼容现状）。
- 软件设置窗口（`renderAppSettings`）加一组单选；改后 `saveAppSettings()`。

**3.3 手动模式的脏数据缓冲（核心新增）**
- 引入 `state.pendingEdits`（或挂在当前视图对象上）：记录 `{rowIndex, field, value}` 列表。
- `manual` 模式下，`makeGanttBarDraggable` 的 `onUp` **不再直接 `updateCell`**，而是：
  1. 计算新起/止值；
  2. 写入 `state.pendingEdits` 并**本地覆盖 `r.values[field]`**（仅前端，用于即时重绘）；
  3. 标记 `state.dirty = true`，视图栏显示"● 未保存"红点。
- 所有读取（渲染、筛选、汇总）使用 `r.values`，因此本地覆盖即时可见，符合"可视化调整"。
- 自动模式：行为不变（直接 `updateCell`）。

**3.4 保存动作**
- 复用/新增"保存数据"按钮（与现有"保存设置"区分）：点击后遍历 `pendingEdits` 逐条 `updateCell`，成功后清空缓冲、去掉脏标记。
- 建议：**自动模式**下拖拽即保存（现状）；**手动模式**下仅"保存数据"按钮（或 Ctrl+S）才落盘。

**3.5 切换/关闭拦截提示（难点）**
- **视图切换（SPA 内部）**：拦截 `switchView`/`setView` 类入口，若 `state.dirty` 则弹原生 `confirm`（或自绘模态）"当前视图已调整但未保存，是否保存？[保存/不保存/取消]"；选保存→先 flush 再切，选不保存→丢弃缓冲再切，取消→中止切换。纯 JS，易实现。
- **关闭软件/窗口（C# 宿主）**：`HtmlMainForm.cs` 的关闭流程需**改为异步**——先向 WebView2 发消息询问 `dirty`，JS 返回需确认时弹出对话框并 `await` 用户决策，再决定是否真正关闭。这是本功能**唯一跨语言协调难点**，需 C# 侧配合（已有 `api.call` 双向通道可复用，但关闭钩子要改）。
- **提示文案**："当前视图已调整（时间/日期）但未保存，是否保存这些更改？"三选项符合用户原意。

### 难度与风险
- **难度：中高（3–5 人日）**。拖拽本身省力，主要成本在 3.3（缓冲与本地覆盖的一致性）与 3.5（关闭拦截的 C#/JS 异步协调）。
- **风险**：
  1. 关闭拦截若只用同步 `confirm`，在 WebView2 宿主关闭事件中可能被忽略或卡死 → 必须走异步确认（C# `await` JS）。
  2. 本地覆盖 `r.values` 后，若发生"筛选/排序/刷新"，需保证缓冲在重算后仍正确应用或提示丢失。
  3. 误操作仍可能发生（用户拖了但忘了保存）→ 提示对话框已覆盖，但建议手动模式下拖拽时条体显示"未保存"视觉态。

### 验证点
- 自动模式：拖拽后单元格值即时变更（现状不变）。
- 手动模式：拖拽后条体移动、单元格显示新值但 Excel 原表未变；点"保存数据"后原表变更；切换视图/关闭时弹确认框；选"不保存"原表保持旧值。

### 实现状态（2026-08-14，v2.9.18 / #402）
- ✅ **已实现并交付**。与原方案差异点（已按落地结果校准）：
  - 开关字段：`APP_SETTINGS.ganttSaveMode = 'auto' | 'manual'`（默认 `auto`，兼容旧行为；写入 `localStorage['mt_app_settings']`，**不触碰用户 `.multiview.json` 设置文件**）。
  - 手动模式：`makeGanttBarDraggable` 的 `onUp` 仅本地覆盖 `r.values` + 标记脏；右下角浮动「保存调整（N）」条提供「保存调整 / 放弃」；切回自动且仍有未保存时自动 flush。
  - 切换视图/数据源：拦截侧栏点击与数据源下拉，弹三选一确认（保存并继续 / 不保存并继续 / 取消）。
  - 关闭软件：`HtmlMainForm.cs` 新增 `setVisualEditDirty` 消息（JS 实时推送脏标记）+ `FormClosing` 拦截 + `HandlePendingVisualEditsOnClose` 异步 MessageBox（保存 / 放弃 / 取消，取消则保留窗口）。
  - 范围：保存模式仅针对"时间/日期数据值拖拽提交"，与视图布局配置的 `saveConfig()` 即时持久化解耦（符合原 §3 纠偏）。
- 软件内「帮助」甘特小节已补充保存模式说明；`verify-build.py` 已加 #402 检查项。

## 4. 功能三：视图另存（保存当前调整为新视图）

### 细化说明
- "当前调整"应明确包含：**筛选条件、分组（groupBy）、字段可见性（visibleFields）、排序、各视图专属 config（cardMeta / ganttConfig / calendarConfig / chartConfig / dashboardConfig）、汇总设置**。即把"此刻看到的布局"固化为一个可一键切换的命名视图。
- 与"保存设置"（覆盖当前视图）不同，"另存为"是**克隆出新视图**，原视图不受影响——满足"不同管理方法"复用。
- 建议同时提供：**重命名、删除、设为默认**，构成完整"视图管理器"。

### 现状
- `state.views` / `cfg.views` 已是视图数组；`saveConfig()` 已序列化绝大多数状态字段（§1）。**数据模型齐备，缺的是 UI 与"当前实时态"的完整捕获**。

### 实现方案
1. **捕获当前态**：取 `activeView()` 的 `cfg` 深拷贝（`JSON.parse(JSON.stringify(cfg))`），得到完整快照。注意：筛选/排序等若部分存于 `state`（如 `state.filter`、`state.sort`）而非 `cfg`，需先回写 `cfg` 再克隆（避免"另存后丢筛选"）。
2. **生成新视图**：分配新 `viewId`（如 `Date.now()` 或 UUID），`viewName` 取自弹窗输入（默认"视图 N"），`viewType` 继承当前类型，推入 `cfg.views` 与 `state.views`，`saveConfig()` 持久化。
3. **视图管理 UI**：
   - 视图切换栏（`renderViewbar`）增加「▾ 视图」下拉：列出所有视图 + 「另存为…」「重命名」。
   - **重命名 / 删除入口优先放进右键菜单（用户补充点 1）**：在视图标签上绑定 `contextmenu`，弹出「重命名 / 删除（仅用户视图可点）/ 设为默认」；基础视图的"删除"项置灰隐藏。难度低（复用现有 `renameView`/`deleteView` 逻辑 + 一个 `contextmenu` 监听），比塞进下拉更直觉，且天然规避"误删基础视图"。
   - 「另存为」→ 弹命名框 → 克隆 → 切换过去。
   - **基础视图不可删除（纠正原描述）**：表格/表单/看板/画册/日历/甘特/仪表盘/图表 8 类为软件**内置基础视图**，必须存在、**不可删除**；只有「另存为」产生的**用户视图**才允许删除（删除前 `confirm` 确认）。因此**无需"至少保留一个"的兜底**——基础视图天然常驻，用户视图可随意增删。这与日历/甘特现有"删除当前统计图表视图"（index.html:2972，仅针对 Chart 用户视图）的范式一致。
4. **与 ② 的协同**：② 的"手动保存模式"缓冲可与"另存为"共用"当前视图快照"能力；建议先把"克隆当前视图"抽成公共函数 `cloneCurrentView()`，② ③ 共用。

### 难度与风险
- **难度：中（2–3 人日）**。模型现成，主要工作是 UI + 实时态完整捕获。
- **风险**：
  1. `state` 与 `cfg` 状态分裂：若筛选/排序只活在 `state`，克隆会丢——需先统一回写 `cfg`（或克隆时合并 `state`）。
  2. 与现有"保存设置"语义混淆：用户可能以为"另存为"会覆盖——UI 文案需区分清楚。
  3. 视图过多时切换栏拥挤 → 下拉 + 搜索更稳。

### 验证点
- 在表格视图设好筛选+隐藏若干列+排序，点"另存为→测试视图"；切换走再切回，布局完整保留；原视图不被改；删除/重命名生效。

## 5. 功能四：HTML 图表视图（加载本地 HTML 模板）

### 方案重新定义（重要）
原描述"显示一个 dash.html 这种本地 HTML 图表"——**不建议硬编码 `dash.html`**（它是固定 demo，无法让用户换模板）。更优方案是新增一种**「HTML 模板视图」类型**：视图 config 存一个 `templatePath`（本地 HTML 文件路径），运行时加载该文件并注入**数据桥**，让用户用不同模板（ECharts / D3 / 自绘）自由展示交互图表。这既保留 `dash.html` 作为内置样例，又开放扩展性。

### 现状
- `dash.html` 已存在（ECharts 风格看板，独立页面）。当前插件仪表盘/图表是 SPA 内用 SVG/简单库自绘，交互与美观受限于内嵌实现。

### 实现方案
**5.1 新视图类型 `HtmlView`**
- `cfg.htmlConfig = { templatePath: '', allowApi: true }`；视图切换逻辑增加 `type==='HtmlView'` 分支。
- 复用现有 `showViewSettings` 增加"模板文件路径"选择（调已有 `api.call('pickFile')` 或 `pickFolder` 模式）。

**5.2 加载方式（二选一）**
- **方案 A（推荐）：`index.html` 内嵌 `<iframe sandbox>`**，src 指向本地文件（经 C# 以 `file://` 或内存流注入）。共享同一 WebView2，宿主轻量。
- **方案 B**：为 HtmlView 单独开一个 WebView2 实例，生命周期随视图进入/退出。隔离更彻底但资源更重。
- 推荐 A：改动小、复用现有 WebView2。

**5.3 数据桥（核心）**
- 向 iframe 注入全局 `window.mtApi`，封装：
  - `mtApi.getRows()` → 返回当前可见行（走 `api.call('getRows')`）；
  - `mtApi.getFields()` → 字段 schema；
  - `mtApi.getConfig()` → 当前视图 config；
  - `mtApi.onFilter(cb)` → 订阅筛选变化（可选）。
- 模板作者在 HTML 中 `mtApi.getRows().then(...)` 取数并用 ECharts 渲染，即实现"现代化交互图表"。

**5.4 安全**
- iframe 必须加 `sandbox="allow-scripts"`（**不含 `allow-same-origin`**，避免模板读宿主）；
- `templatePath` 限定在白名单目录（如工作簿同目录 / 指定模板库），禁止任意路径；
- `mtApi` 仅暴露只读取数接口，禁止模板直接写表（防止恶意模板破坏数据）。

**5.5 与现有仪表盘关系**
- 不替代现有仪表盘（其简单、零依赖、稳定）；HTML 视图作为"高级/自定义"补充，面向需要复杂交互图表的用户。

**5.6 推荐采用「模块化五层分离」结构（参考 `大屏结构说明.md`，用户补充点 2）**

为让"配色方案 / 模板 / 框架"都能独立切换、改任一类不牵动整体，建议直接借用用户已有的 `大屏结构说明.md` 中验证过的结构：把一份动态图表拆成 **引擎壳 / 渲染库 / 数据 / 主题(配色) / 全局设置 / 布局(模板)** 六类，各自外置为独立文件/对象：

| 关注点 | 对应模块（参考 `大屏结构说明.md`） | 在 HtmlView 模板里怎么落 |
| --- | --- | --- |
| 框架（怎么画） | 引擎壳 `项目管理大屏示例.html` 的 `CHARTS` 注册表 | 通用引擎壳；新增图表类型只在注册表登记一项，引擎零改动 |
| 渲染库 | `echarts.min.js`（位置可本地/共享/CDN） | 模板统一引用，位置可配（加载器按 `./`→`../libs/`→CDN 顺序回退） |
| 数据 | `data.js` → `window.DASH_DATA` | 由 `mtApi.getRows()` 注入，模板只读 `DATA` 不写死数字 |
| 配色方案 | `theme.js` → `window.DASH_THEME`（palette/axis/grad…） | 抽成独立配色对象，切换配色不碰其它 |
| 全局设置 | `settings.js` → `window.DASH_SETTINGS` | 标题行/卡片圆角/时间格式/宽高策略(`fluid`\|`fixed`) 等集中放 |
| 模板(布局) | `layout.js` → `window.DASH_LAYOUT` | 几行几列、每格图表、标题文字，按模板切换 |

- **价值**：改配色只动 `theme`、换布局只动 `layout`、换数据只动 `data`，互不影响——正是用户要的"修改任一类无需修改整体，更方便数据修改、样式/布局切换"。
- **宽高策略**：复用 `settings.sizing.mode`（`'fluid'` 自适应跟随页面 / `'fixed'` 按设计分辨率 `transform:scale` 等比铺满）——投大屏 LED 用 `fixed`，日常网页用 `fluid`，与 `大屏结构说明.md` 第七节一致。
- **落地建议**：将内置 `dash.html` **重构为上述模块化结构**（引擎 + `data/theme/settings/layout` 四文件），作为首个内置模板；`htmlConfig.templatePath` 指向"模板目录"而非单个 HTML，目录内自带这 5 个文件。用户/社区此后可只换 `theme`/`layout` 就产出不同风格看板，扩展性、美观度上限大幅提升。
- **异常兜底**：该结构本身要求"每格类型未注册/数据集缺失/渲染报错只在该格红字提示、不连累整屏"——与插件现有容错思路一致，可直接沿用。

### 方案价值评估
- **高价值**：彻底解耦图表表现层与插件内核，用户可自研/社区共享模板，扩展性、交互性、美观度上限大幅提升；`dash.html` 可直接作为首个内置模板。
- **适度成本**：核心是"模板加载 + 数据桥 + 沙箱"，无算法难点，属工程整合。

### 难度与风险
- **难度：中（3–4 人日）**。
- **风险**：
  1. 本地文件 `file://` 在 WebView2 的 origin 限制（与画册图片同因）→ 需 C# 侧以 `NavigateToString` 注入或 `WebResourceRequested` 拦截提供内容。
  2. 模板与 `mtApi` 版本耦合：模板升级时需向后兼容。
  3. 性能：大表 `getRows` 全量返回可能卡 → 建议分页/聚合接口。

### 验证点
- 选 `dash.html` 作为模板，HtmlView 正确渲染且数据随表格变化；沙箱下模板无法访问 `document.cookie`/宿主 DOM；切换出 HtmlView 时 WebView2 资源释放。

## 7. 公共风险与工程建议

1. **交付链路铁律**（历史踩坑）：改动只改 `index.html` 后必须 `dotnet build -c Release` → 拷贝 DLL 到 `dist/files` → `verify-build.py` 校验；Excel/WPS **运行时缓存 DLL，只重开任务窗格不重载**，验证须完全退出宿主再重开。新增字符串/类名务必同步 `verify-build.py` 检查串。
2. **设置持久化一致性**：`APP_SETTINGS`（软件级）与 `cfg`（工作簿/视图级）分两套保存通道，新增开关别放错层；手动保存模式的脏标记应挂在 `state`（运行时）而非 `cfg`（持久化），避免误存。
3. **数据桥稳定性**：② 的 `updateCell`、④ 的 `mtApi.getRows` 都依赖 `api.call` 通道，改动需保证失败回滚（现有 `catch` 已 toast，手动模式需额外在 flush 失败时保留 `pendingEdits`）。
4. **跨语言关闭拦截**：② 的窗口关闭确认必须 C# 异步 `await` JS 决策，禁止同步 `confirm` 阻塞宿主线程。

## 8. 附加分析：Ctrl+滚轮缩放控制可行性（用户补充点 3）

### 现象
各视图下按 `Ctrl`+滚轮会缩放整个 WebView2 页面（浏览器原生缩放），属高频误触操作；用户希望"避免无操作"或"仅限定某些视图可用"。

### 根因（已定位代码）
`HtmlMainForm.cs` 初始化 WebView2 时（约 185–189 行）只设置了 `AreDefaultContextMenusEnabled / AreDevToolsEnabled / IsStatusBarEnabled / IsWebMessageEnabled`，**未设置 `IsZoomControlEnabled`**，故取默认值 `true`——浏览器接管 `Ctrl`+滚轮为整页缩放。`index.html` 内无任何自定义缩放代码，印证这是 WebView2 原生行为，而非 SPA 逻辑。

### 结论：可控，且有两种粒度
1. **全局关闭（最简、推荐先做）**：在 `InitializeAsync` 的 Settings 块加一行
   `_webView.CoreWebView2.Settings.IsZoomControlEnabled = false;`
   即可彻底禁用浏览器原生缩放，消除所有视图下的误触。改动 1 行、不触及 `index.html`、零回归风险。
2. **按视图限定（进阶）**：禁用内置缩放后，在 `index.html` 自行实现"仅特定视图可缩放"——
   - 监听 `wheel` 事件，当 `e.ctrlKey` 时 `preventDefault()` 阻止默认；
   - 依据 `activeViewType()`（已存在，约 805 行，返回 `'Table'/'Gantt'/'Chart'/…`）判断是否启用：基础视图（表格/表单等）直接吞掉事件；图表/仪表盘类则对视图容器施加 CSS `transform: scale(因子)` 自定义缩放（因子存 `APP_SETTINGS` 或 `state`）。
   - 实现成本约 0.5–1 人日，纯前端。

### 建议
先上方案 1（全局关闭，零风险）；若后续确需"图表视图内缩放看细节"，再上方案 2（仅图表类启用自定义缩放）。两者都在插件内闭环，无需改动宿主 Excel/WPS。
> 注：禁用内置缩放不影响截图链路——`HtmlMainForm.cs` 截图走 CDP `Page.captureScreenshot`（约 430 行），与 `IsZoomControlEnabled` 无关。
