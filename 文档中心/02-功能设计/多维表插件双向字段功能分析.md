# 多维表：金额、单价、数量联动计算字段设计

双向联动就等价于 Access 窗体多个控件的 `AfterUpdate` 事件处理程序：**只在窗体控件交互时执行计算，回填其他控件；数据源本身没有任何自动计算约束，保存动作才把界面结果落地到数据源。**
> 
> 业务规则：
> 数量 × 单价 = 金额
> 
> 
> - 用户输入【数量】+【单价】→ **自动算出金额**
> - 用户输入【数量】+【金额】→ **自动算出单价**
> 
> 
> Excel 原生：靠单元格公式；多维表不能直接用 Excel 公式，需要自己实现**互斥联动计算字段**，这不属于普通手动输入字段，也不是简单只读公式字段。

## 核心难点（和普通公式字段不一样）

普通公式字段：**只读，用户不能改，只能由其他字段算出结果**。
但这个业务是**双向互算**：

1. 修改 A、B → 更新 C
2. 修改 A、C → 更新 B

> 
> 会出现循环依赖，不能直接套用普通公式引擎，必须定义「哪个字段是用户手动输入，哪个是推导出来」。

> 
> 举冲突例子：
> 数量 = 10；单价 = 2；金额 = 20
> 用户直接把金额手动改成 30。
> 此时：到底是重新反算单价 (30/10=3)？还是把金额当成手动输入，锁定金额不再自动计算？
> 这是所有多维表做双向计算必须解决的业务边界。

## 方案设计（可直接写入 MD 文档）

```
# 双向联动计算字段：数量‑单价‑金额
## 业务说明
三个字段：数量(数字)、单价(数字)、金额(数字)
逻辑：
金额 = 数量 × 单价
单价 = 金额 ÷ 数量

### 关键约束：必须有一个【受控推导字段】标记
不能三个字段全部开放手动输入又互相计算，会产生循环歧义。
> 设计方案：提供配置项，由用户选择**哪一个字段为自动推导字段（只读，不允许手动编辑）**
三种模式二选一：
模式1：【金额为推导字段】✅最常用
- 用户手动输入：数量、单价
- 金额自动计算，界面禁止直接编辑金额；修改数量/单价，金额同步刷新。

模式2：【单价为推导字段】
- 用户手动输入：数量、金额
- 单价自动计算，界面禁止直接编辑单价；修改数量/金额，单价自动反算。

模式3：全部手动输入（关闭联动）
- 数量、单价、金额全部允许手动录入，不执行自动计算。

> ❌禁止：三个字段同时允许手动输入同时双向计算，会出现逻辑冲突。

## 触发时机
1. 在多维表窗体/详情面板修改字段值，失去焦点、或者回车确认后触发联动。
2. Excel源超级表同步过来的数据：**不执行自动重算**。
> 说明：源Excel已经存在公式计算结果，插件只读取已有值，不覆盖源数据；联动计算仅发生在插件界面内部编辑记录的时候。

## 边界条件
1. 数量 = 0
   除法会除零错误，此时推导字段置空，UI展示提示：“数量不能为0，无法计算”。
2. 任意一个输入字段为空：推导字段置空。
3. 输入非数字文本：标记字段异常，不执行计算。
4. 小数精度：配置可设置保留小数位数（金额一般2位小数），四舍五入。

## 与Excel超级表的交互（你的插件重点）
1. 从Excel超级表导入：数量、单价、金额都是普通数字字段，导入时**不自动开启联动**。
2. 用户在插件中手动开启「双向联动配置」，绑定这三个字段。
3. 在插件UI编辑记录，触发联动计算后，保存回写Excel超级表对应单元格。
4. 如果Excel表格本身写了公式：插件回写会覆盖单元格公式，变成静态数值。
> ⚠️重要提示，UI需要提示用户：开启联动保存回写Excel后，原单元格公式会丢失，转为普通数值。

## UI需要的控件配置（WPF）
1. 在字段设置弹窗，增加【双向联动计算】配置面板
2. 选择：数量字段、单价字段、金额字段（从当前数据集数字字段下拉选择）
3. 单选框选择：推导字段 → 【金额 / 单价 / 关闭联动】
4. 设置金额小数位数。

## 数据存储
在多维数据集元数据中保存配置，不是保存在单条记录：
```json
{
  "enableBidirectionalCalc": true,
  "qtyField":"数量",
  "priceField":"单价",
  "totalField":"金额",
  "deriveField":"total", // total=金额推导，price=单价推导，null关闭
  "decimalPlaces":2
}
```

> 
> 元数据属于数据集配置，不是每一行数据，所有记录共用同一套联动规则。

## 编辑记录执行流程

1. 用户在详情面板修改【数量】，回车 / 失去焦点
2. 判断联动配置是否开启
3. 获取另外两个输入字段的值，校验是否合法数字，校验数量≠0
4. 根据配置的 deriveField，计算推导字段的值
5. 将计算结果赋值到 UI 控件，内存数据集更新该行
6. 用户点击保存，将整套数值回写到 Excel 超级表。

## 限制说明

1. 该联动仅在插件 WPF 详情编辑窗体生效；直接在 Excel 表格修改单元格，不会触发这套联动。
2. 不支持部分行开启联动、部分行关闭；整个数据集统一一套联动规则。

```

## 和市面上多维表对比
1. 飞书多维表：**没有原生双向互算字段**。飞书只支持单向公式字段（只读）。想要双向，只能用脚本自动化。
2. WPS多维表：同样只有单向公式，不支持双向互算；
> 也就是说：**这个双向联动是你插件的增强能力，原生多维表组件本身没有这个能力，需要自己实现业务层逻辑**。

## 开发必要条件清单
1. 数据集内必须存在3个**数字类型字段**（数量、单价、金额），不能是文本。
2. 数据集元数据层，存储这套联动配置。
3. UI层：详情窗体编辑控件，监听控件失去焦点/值变更事件；**推导字段输入框设置IsReadOnly=True，禁止手动输入**。
4. 业务层计算函数：做数字校验、除零保护、小数舍入。
5. 回写Excel时的风险提示：会覆盖原有Excel公式。
6. 同步Excel超级表数据时：只读取，不自动重算，避免把Excel原有数据覆盖。

### 伪代码片段（C#逻辑）
```csharp
// 配置：deriveField = total 代表金额是推导字段
if(config.EnableBidirectionalCalc && config.DeriveField == "total")
{
    decimal qty = GetFieldDecimal(row, config.QtyField);
    decimal price = GetFieldDecimal(row, config.PriceField);
    decimal total = qty * price;
    SetFieldValue(row, config.TotalField, Math.Round(total, config.DecimalPlaces));
}
// deriveField = price，单价为推导字段
else if(config.DeriveField == "price")
{
    decimal qty = GetFieldDecimal(row, config.QtyField);
    decimal total = GetFieldDecimal(row, config.TotalField);
    if(qty == 0)
    {
        SetFieldValue(row, config.PriceField, null);
        ShowWarning("数量不能为0，无法计算单价");
    }
    else
    {
        decimal price = total / qty;
        SetFieldValue(row, config.PriceField, Math.Round(price, config.DecimalPlaces));
    }
}
```

## 产品建议

1. 默认**关闭双向联动**，用户手动去字段设置里面打开，不要导入 Excel 自动开启。
2. 推导字段的输入框 UI 上要视觉标记（灰色背景），告诉用户这个是自动计算，不能手动改。
3. 一定要做除零、空值、非数字的容错，不然编辑窗体直接异常崩溃。
4. 弹窗提示：保存回写到 Excel，会覆盖单元格原有公式。

# 双向联动计算（数量‑单价‑金额）性能瓶颈、隐性问题、冲突点

承接上一节设计，这部分可以直接追加到 MD 文档。

> 
> 核心：**它不是数据库底层计算，是 UI 编辑层业务逻辑，只在编辑单条记录时触发；大批量场景、同步 Excel、批量导入、批量修改会暴露出很多隐性坑**。

## 一、性能限值 & 瓶颈

### 1. 正常单条编辑场景（用户打开详情窗体改一条记录）

性能几乎无损耗。

- 仅做简单乘除、小数舍入；只操作当前行内存对象。
- 无论数据集几千行，**只处理当前编辑行，和总数据量无关**。
👉 单条编辑：无性能压力。

### 2. 会产生性能压力的场景

1. **批量修改（批量更新多条记录）**
如果批量修改「数量」字段，代码循环每一行执行联动计算：

- N 条记录就要跑 N 次计算逻辑；上万条批量修改会有明显延迟。

> 
> 风险：如果再同步回写 Excel 超级表，Excel‑DNA 频繁写单元格，会进一步放大卡顿。

2. **从 Excel 超级表刷新全部数据**

> 
> ⚠️这里有一个重大陷阱：
> 千万不要**刷新时对全部行自动重算联动**。

- 上万行全部执行乘除，CPU 占用飙升；
- 更严重：Excel 源本身有自己的数值 / 公式，插件重算会覆盖原始读取进来的金额 / 单价，篡改源数据。
✅正确规则：**仅在插件 UI 手动编辑单条记录时触发联动；数据刷新、导入、批量加载，不执行联动计算**。

3. 大量同时打开编辑窗体
一般桌面插件不会同时开大量编辑窗口，该问题影响很小。

> 
> 性能总结：
> ✅单条编辑：无瓶颈
> ⚠️批量更新、大批量重算：会产生开销，需要做逻辑限制，禁止自动全表重算。

## 二、隐性业务逻辑问题

### 1. 循环歧义（最核心隐患）

虽然我们配置了一个「推导字段只读」来规避循环；但依然有边界场景：

- 用户 A 模式：推导字段 = 金额（金额只读）
- 外部 Excel 手动修改金额，同步回插件数据集。

> 
> 此时：Excel 改了金额，但是插件配置金额是推导字段，**插件不会自动反算单价**。
> 数据出现矛盾：数量 = 10，单价 = 2，金额被 Excel 改成 30；三者对不上。

**现象：插件 UI 内是正确联动；但是 Excel 直接改源表，会出现字段数据不一致。**
处理方案：

1. 联动逻辑**只属于插件 UI 编辑层，不管控 Excel 源文件**。
2. 在元数据提示：开启双向联动后，建议尽量不在 Excel 原生界面修改推导字段。
3. 在校验模块增加数据校验功能：可以一键检查全表，找出「数量 × 单价≠金额」的异常行，标记出来给用户修正。

### 2. 小数精度累积误差

`decimal`计算也会出现：

> 
> 数量 = 3，单价 = 0.1 → 0.30000000000000004
> 四舍五入处理不到位，回写到 Excel，金额出现很多位小数。
> 对策：

- 计算完成立刻按配置小数位`Math.Round`；
- UI 展示、回写 Excel 都使用舍入之后的值；
- 不要把原始高精度浮点数直接存入行对象。

### 3. 除零、空值、非法值连锁问题

- 数量 = 0 → 单价推导为空；
- 数量为空，填写单价、金额 → 推导字段为空；
- 某字段填入文本（脏数据），计算直接中断。

隐性坑：如果代码没有做空判断，会把`null`参与运算，直接 WPF 窗体抛出异常崩溃。

> 
> 每一次联动计算前，必须先做值校验。

### 4. 舍入带来业务分歧

举例：
单价 3.33，数量 3；
3.33 ×3 =9.99；
如果用户手动输入金额 = 10。

- 模式：推导字段为单价：金额 = 10，数量 = 3 → 单价 = 3.33333…
保存回 Excel，保留 2 位小数单价变成 3.33，再次打开联动计算，金额又变成 9.99。

> 
> 来回修改，数值会来回跳动。

对策：
文档写明风险；提供配置项控制小数位数；数据校验功能提示存在舍入偏差的记录。

## 三、和其他模块的冲突

### 冲突 1：Excel 超级表同步 / 回写

1. 开启双向联动，在插件编辑保存，回写 Excel，**会把单元格公式覆盖为静态数值**。

> 
> 用户原先 Excel 写的`=A2*B2`公式直接丢失，变成固定数字。
> 用户如果不知情，会以为 Excel 还会自动计算，结果 Excel 不再变动。
> ✅必须弹窗提示，并且在字段配置界面醒目标注该风险。

2. Excel 超级表外部修改数据，同步进插件，**不会触发联动**，会产生三组数值互相不匹配。

> 
> 联动不是数据库约束，只是 UI 编辑事件，底层数据不会自动校验修复。

### 冲突 2：与公式字段冲突

如果用户同时把「金额」设置成普通单向公式字段。

> 
> 公式字段会覆盖双向联动的计算结果，两套计算逻辑打架。

约束：

> 
> 同一个字段，不能同时是【双向联动推导字段】和【普通公式字段】。
> 在配置界面做互斥判断，开启双向联动时，禁止将 qty/price/total 三个字段设置为普通公式字段。

### 冲突 3：批量导入 / 批量粘贴数据

批量导入一批记录，导入逻辑**不会执行双向联动**。
导入后，会出现大量记录：数量、单价、金额三者数值不一致。

> 
> 用户会误以为导入会自动补齐金额，实际不会。
> 对策：
> 提供一个手动工具按钮：【对全部记录执行联动重算】，交给用户主动点击，不自动执行。

### 冲突 4：查询视图、筛选、仪表盘统计

联动只是编辑时更新内存行对象；更新完成内存数据会同步，查询、筛选、仪表盘可以读到新值，**这部分没有冲突**。

> 
> 只要修改行的时候同步更新内存模型，其他视图完全正常。

### 冲突 5：撤销 / 回退逻辑

用户在编辑窗体，修改数量，自动算出金额；用户点撤销。
隐性问题：不仅要撤销数量，同时也要撤销推导字段的金额。

> 
> 如果只还原数量，金额还保留计算后的值，数据不一致。
> 编辑窗体的撤销，需要把**参与联动的全部三个字段一起做快照保存**，不能只保存修改的那一个控件。

## 四、并发 / 多窗体冲突（你的插件场景）

1. 同时打开两条记录的编辑窗体，修改两条记录的数量：互不影响，没有问题。
2. 一边 WPF 编辑窗体打开记录，一边直接在 Excel 表格修改同一行超级表单元格。

> 
> 两个来源同时修改同一条记录，会发生数据竞争，保存的时候会互相覆盖。
> 这属于 Excel‑DNA 插件通用问题，不只是双向计算特有。

## 性能限值
1. 单条记录编辑场景：仅操作当前行，性能无压力，不受总数据集行数影响。
2. 批量修改多条记录：每一条记录都会执行计算逻辑，上万条批量更新会产生CPU开销；叠加Excel回写会进一步卡顿。

1. 联动仅在插件WPF编辑窗体触发；直接修改Excel源超级表，不会执行联动，会出现「数量/单价/金额」三者数值互相矛盾。

1. 与Excel超级表冲突

    - Excel直接修改源数据，不会触发联动计算。
2. 和普通单向公式字段互斥
    - 参与双向联动的三个字段（数量、单价、金额），不允许再设置为普通公式字段，两套计算逻辑会互相覆盖。配置UI增加互斥校验。
3. 批量导入/粘贴

## 边界约束
1. 联动属于UI层业务逻辑，**不是底层数据约束**，底层数据集本身不会自动保证数量×单价=金额。
2. 联动配置是数据集全局配置，不支持部分行开启、部分行关闭。
3. 推导字段在UI设置只读，但是底层内存模型仍然允许写，代码层面要防止绕过UI直接修改推导字段。

## 开发落地建议

1. 不要把双向联动当成底层数据库能力，它本质是**编辑窗体的事件业务逻辑**，这点在开发时心里要有数。
2. 不要迷信联动一定保证数据正确，增加「数据校验」功能，用来扫描找出不符合`数量*单价=金额`的脏行，这是兜底手段。
3. 所有重算全部交给用户主动触发，不要后台偷偷自动跑。
1. 如果后台 C# 代码直接修改内存 Row，**不要指望联动会自动生效**。后台修改行，需要手动调用计算方法才会更新推导值。
2. 不要把联动逻辑写在数据集的 Set 属性里面，千万不要；那样就变成底层自动触发，会造成批量加载、刷新的时候疯狂执行计算，引发之前说的性能、篡改数据问题。

> 
> ✅联动逻辑固定放在**窗体控件事件层**，不要下沉到数据集模型内部。

# 关于双向联动计算字段的产品思考
> 主流多维表格（飞书、WPS多维表、Airtable）没有提供原生双向联动字段。
## 根本原因
1. 双向联动本质是【窗体编辑层事件逻辑】，类似Access窗体AfterUpdate更新后事件，强绑定窗体控件交互；
    而多维表字段属于数据表全局元数据，不绑定任何编辑窗体。
2. 存在业务歧义：当三个字段都有值，系统无法判定应该覆盖哪一个字段，没有统一标准答案。
3. 底层公式引擎依赖单向字段依赖图，双向计算形成循环依赖，批量刷新、导入、API写入场景无法处理。
4. 多维表数据来源非常多（表格直接编辑、导入、API、自动化、多人协同），很多场景不经过编辑窗体，无法触发联动逻辑，容易产生脏数据。
5. 用户理解成本高，普通使用者很难区分“什么时候会自动计算、什么时候不会”，容易产生大量误解和问题反馈。

## 本插件实现该功能的前提约束
本插件可以实现双向联动，得益于产品形态的特殊性：
1. 联动逻辑仅作用于WPF详情编辑窗体，推导字段UI层面设置只读；
2. 明确文档提示：直接修改Excel源超级表、批量导入不会触发联动，会产生数据不一致；
3. 提供数据校验工具，扫描全表，标记不满足计算公式的异常行，作为兜底。
> 该功能属于窗体层增强能力，**不是底层数据强制约束，不能保证所有场景下数据自动正确**。

## 对比主流产品的替代方案
1. 单向公式字段：金额=数量*单价；金额只读，无法反向反算单价。
2. 脚本自动化：监听记录更新事件，脚本实现联动，需要用户自行维护脚本。
