# 月视图事件（任务/项目）重叠布局方案分析

> 版本背景：v2.9.26（MonthFloatSeg）月视图已改为「绝对定位悬浮分段层」，但**重叠处理仍有结构性缺陷**。
> 说明：下文「任务」「项目」同义，均指带起止日期的区间事件（如 A=7-1~7-20、B=7-5~7-10）。

---

## 一、问题现象与根因定位

### 现象
月视图中，当两个任务的日期区间存在交集（如 A=7-1~7-20、B=7-5~7-10，交集 7-5~7-10），二者在交集区段出现**视觉重叠**。

### 当前代码核对（`index.html`，`layoutMonthEvents` 约 2287–2314 行）
```js
var maxLanes=APP_SETTINGS.monthMaxEvents||5;        // ← 硬上限 = 5
var bandLanes=[ [],[],[],[],[],[] ];                // 6 个周 band（月最多 6 周）
function pickLane(bands){
  for(var l=0;l<maxLanes;l++){ /* 找空泳道 */ }
  return 0;                                          // ← 满 5 后回退 lane 0：重叠来源
}
```

- **泳道分配本身是「按周 band + 贪心首适（greedy first-fit）」**，逻辑正确：A、B 两个事件会被分到 `lane 0` / `lane 1`，**理论上不重叠**。
- **真正的重叠来源**：当某一周（band）内**同时段任务数 > 5** 时，`pickLane` 遍历完 lane 0~4 均被占用，执行 `return 0`，第 6+ 个任务被强行塞回 lane 0，与 lane 0 的任务**碰撞重叠**。这正是你看到「重叠」的结构性原因（你举的 A/B 只是示意，真实数据里该周多半有 5+ 个并行任务）。
- 附带问题：泳道数被 `monthMaxEvents` 写死为 5，既可能「过多时重叠」，也可能「稀疏时浪费高度」（其实 2 个就够了，却预留了 5 行的概念高度）。

## 二、业界主流方案调研（搜索结论）

| 来源 | 做法 | 要点 |
|------|------|------|
| **区间图着色 / LeetCode 253 会议室问题** | 最少所需「房间/泳道」数 = 任意时刻**最大重叠数**（最大团） | 理论下界；扫描线 O(n log n) 可求[1][2] |
| **Google Calendar 周/日视图** | 按 start 升序排序，每个事件分配「最早可用 lane」（该 lane 上一事件结束 ≤ 本事件开始）；左偏移 `lane/总数`、宽度 `1/总数` | 并排列（side-by-side）；月视图因格子窄改用**行堆叠**[3][4] |
| **FullCalendar 月视图（dayGrid）** | `dayMaxEvents` / `dayMaxEventRows` 限制每行可见条数，超出显示「**+N 更多**」弹出 | 用「折叠 + 更多」兜底极端密度，窗口高度固定[5] |
| **Algorithm::TimelinePacking（Perl）** | 通用区间→行贪心装箱，含最小间隔 `space` 参数 | 与「泳道 + 间隔」思路一致[6] |

**核心共识**：
1. 重叠靠**泳道（lane）分配**解决，不是靠压缩宽度（月视图格子太窄，只能上下堆叠行）。
2. **泳道数应为动态 = 该时段最大重叠数**，而非固定上限。
3. **极端密度用「+N 更多」折叠**，避免把整月视图撑爆。
4. **相邻泳道留间隔**（如你方案 3 的 3px）是通用做法。

## 三、你的方案拆解与评估

### 方案 1：每任务占一行，重叠则分行
✅ **正确方向**，等价于业界「泳道分配」。当前代码已有雏形，只需把「固定 5 上限 + 回退 0」改为「动态泳道数 = 该 band 最大重叠数」。

### 方案 2：无任务的周按最小高度，把空间让给密集周
⚠️ **方向对，但需在「固定 6 行网格」约束下实现**。当前月视图是 6 行 × 7 列固定网格，事件层绝对定位于网格之上；若某周有 8 个泳道，段会向下溢出到下一行的日期数字上。
- **推荐改法：总高度预算不变**，按各周「最大泳道数」比例分配每周行的可用高度（密集周多分、空白周给最小高度）。这样既「不改变整体窗口」又自然消除向下溢出，比「整周隐藏」更稳（月视图格子本身需保留日期数字）。

### 方案 3：行间距 3px（≥2 任务时）
✅ **低成本高收益**，直接采纳。仅当该 band 泳道数 ≥2 时加 `gap`，单任务时不留白避免浪费。

### 另一种方案（方案 B）：不改布局，重叠区短任务置顶 + 按层填色
❌ **不推荐作为主方案**，原因有数学硬伤：
- 你举的例子 A[1-1,1-20]、B[1-8,1-15]、C[1-10,1-12] 恰好是**干净嵌套**（C⊂B⊂A），能分出 3 层；但你已正确指出「并非每个项目都完全在另一个内部」。
- 一般区间重叠图**不是层状族（laminar family）**：例如 A[1-1,1-20]、B[1-5,1-12]、C[1-10,1-25] —— C 起始在 A 内却结束在 A 外，三者两两相交但互不包含。此时「层号 = 嵌套深度」**无法良定义**，按层填色会产生语义混乱（同一层里既是最长又是被包者）。
- 月视图格子窄，并排列不可行，方案 B 的「短在上、长在下」本质仍是行堆叠的变体，既没解决重叠（只是排序），又引入配色复杂度。
- **可保留其精华**：用「按 lane 索引循环调色板」做纯视觉区分（不表达层级语义），规避层叠不闭合问题。

## 四、推荐综合方案（融合你的 1/2/3 + 业界最佳实践）

> **核心：把「固定 5 泳道 + 回退 0」升级为「区间图着色动态泳道 + 跨 band 锁 lane + 行高自适应 + 3px 间隔 + 极端密度 +更多」。**

1. **动态泳道数（根治重叠）**
   - 对每个周 band，用扫描线求该 band 内**最大重叠数 = 所需泳道数**（理论最小，LeetCode 253）。
   - 取消 `monthMaxEvents` 的硬截断；`pickLane` 不再 `return 0`，而是按需扩展 `bandLanes[bn]` 数组长度。
2. **跨 band 锁定 lane（已具备，保留）**
   - 当前每个事件在其所有 band 内共用同一 `lane`（2287–2313 已是单 lane 贯穿），跨周不断裂，保持。
3. **行高自适应（落地方案 2）**
   - 该 band 事件层高度 = `maxLane(band) × (MT_LANEH + gap)`。
   - 月度 6 行**总高度预算固定**，按各周 maxLane 比例分配行高：密集周高、空白周压到最小（如仅容日期数字）。既「不改整体窗口」又消除向下溢出。
4. **3px 泳道间隔（方案 3）**
   - 新增 `MT_LANEGAP=3`，仅当 `maxLane(band)≥2` 时计入；单任务时 `gap=0`。
5. **lane 调色板（方案 B 的精华、去层叠语义）**
   - 按 `lane` 索引循环取一组低饱和色（lane0 浅蓝 / lane1 浅绿 / …），纯区分不表层级。可设 `APP_SETTINGS.monthLanePalette`。
6. **极端密度兜底「+N 更多」**
   - 当某 band `maxLane` 超过可视阈值（如 5~6），仅渲染前 N 条 + 底部「+M」小条；点击展开浮层看全部（FullCalendar/Google 同思路）。保证即便有 20 个并行任务，月视图也不崩。

### 方案对比小结
| 维度 | 现状(v2.9.26) | 方案1+2+3 | 方案B | 推荐综合 |
|------|------|------|------|------|
| 重叠消除 | ✗（>5 碰撞） | ✓ | △（只排序不消除） | ✓ |
| 行数来源 | 固定 5 | 动态=最大重叠 | 不变 | 动态 + 比例行高 |
| 窗口高度 | 固定 | 固定 | 固定 | 固定 |
| 极端密度 | 崩 | 撑爆 | 不变 | +N 更多兜底 |
| 配色语义 | 按字段 | 按字段 | 按层（不闭合） | 按 lane（无语义歧义） |

## 五、与现有代码映射（待你确认后再改）

- `layoutMonthEvents`（2287）：`maxLanes=APP_SETTINGS.monthMaxEvents||5` → 改为**每 band 动态求最大重叠**；`pickLane` 的 `return 0` 改为「扩展 lane」。
- `makeMonthSeg`（2315）：`top=c0.offsetTop+MT_PADTOP+lane*MT_LANEH` → 加 `+lane*MT_LANEGAP`（gap 由 band 决定）。

## 六、结论

1. 你提出的**方案 1（分行）+ 方案 2（空白周让高）+ 方案 3（间隔）组合是正确主线**，与业界「区间图着色泳道」一致。
2. **方案 B 的层叠填色因一般区间图非层状族而语义不闭合**，不宜作主方案；其「多色区分」可降级为「按 lane 调色板」保留。
3. **根因 bug**：当前 `maxLanes` 写死 5 且 `pickLane` 回退 0，是重叠的直接来源；改为动态泳道即可根治。
4. **建议下一步**：先按「五」做最小改造（动态泳道 + 3px 间隔）消除重叠，再按需加行高自适应与「+N 更多」。
