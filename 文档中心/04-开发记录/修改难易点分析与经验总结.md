# 多维表分析软件 — 修改难易点、困难与经验总结

> 编写时间：2026-08-14  
> 依据：项目任务清单 #1 – #374（累计 374 项，已完成 316，在途 2，待办 56）  
> 目的：复盘哪些地方难改、哪些地方被反复修改、踩过哪些坑、沉淀可复用经验。

---

## 一、修改分布画像

从 374 项任务的主题分布看，工作量高度集中在**交互密集视图**与**构建交付链路**：

| 主题聚类 | 大致任务量 | 难度 | 返工频度 |
|----------|-----------|------|----------|
| 日历视图（尤其任务条拖拽） | 极多（约 60+ 项） | 高 | 极高 |
| 甘特视图（维度/着色/平移/边界） | 多（约 50+ 项） | 高 | 高 |
| 设置体系（软件级 ↔ 文件级拆分） | 中（约 30+ 项） | 中 | 中 |
| 图标与功能区 | 中（约 10+ 项，但多次重选） | 低 | 中 |
| 构建 / 校验 / dist 更新 | 多（贯穿全周期） | 中 | 高（每次改动必走） |
| 字段开关 / 显隐 / 排序 | 多（约 40+ 项） | 中 | 高 |
| 表单视图（录入/对齐/联动） | 中（约 25+ 项） | 中 | 中 |
| 导出（图片/剪贴板） | 少（约 8 项） | 高 | 低 |

**结论**：日历拖拽与甘特是「又难又常被返工」的核心区；构建校验链路是「每次改动都要重走、最易出错」的必经区；图标虽然简单，但因审美/需求变动被多次重选。

## 二、修改难度分级

### 🟢 易改（局部、低风险）
- 文案/标签改名（如 #369「图表卡片操作按钮」→「图表控制开关」）
- 简单样式微调（间距、对齐、颜色）
- 常量/默认值（如 #370 月视图任务数默认值）
- 删除一个未启用的 UI 控件（如 #367 删除仪表盘顶部阈值控件）

> 特点：改完 `verify-build.py` 同步一处校验串即可，几乎不牵动其它逻辑。

### 🟡 中等难度（需理解上下文）
- 设置项的「软件级 ↔ 文件级」归属调整（#287, #288, #346, #366）：要同时改默认值、`saveAppSettings`/`saveConfig`、读取处三处，且容易漏改导致「设置没生效」。
- 字段开关 / 显隐 / 排序：每个视图都有自己的状态读写，改动要逐视图核对。
- 表单视图录入与右侧面板联动（#172, #202, #224, #238）：焦点、双输入（日期+时间）、实时跟随。
- 图标替换（#158, #193, #216, #234, #273）：检索→预览→替换资源→重建，流程固定但琐碎。

### 🔴 难改（牵一发动全身 / 数学复杂 / 平台耦合）
- **日历任务条拖拽**（#145, #148, #149, #154, #173, #174, #280, #293, #298, #306, #347, #348, #349）：涉及鼠标坐标→日期/时间换算、按天/按周吸附、左缘/右缘/中部不同语义、月视图横向+纵向拖拽、松手回写 Excel。
- **甘特多维度渲染与平移**（#286, #303, #320, #327, #345, #350, #357）：年/季/月/周刻度生成、今日红线位置、水平滚动条、显示边界（飞书模式 + 外扩 N 天）。
- **导出裁剪 + 手写 PDF（#376 已移除）**（#367 – #370, #376）：WebView2 整页截图坐标映射、手写最小 PDF（FlateDecode + Predictor 15 + zlib）、无第三方库约束；#376 因位图为栅格（非矢量）依需求移除 PDF 导出，导出仅保留图片(PNG)与剪贴板。
- **构建交付链路**（全局易错点）：`dotnet build` 产物 → `dist/files` 拷贝 → `verify-build.py` 编码校验，任何一步错位都导致「改了没生效」或「校验 FAIL」。

## 三、高频修改区域 TOP（按返工次数）

1. **日历拖拽交互** —— 被反复打磨十余轮。早期只做「单击切换视图」，后逐步加「月视图左右拖拽改起止」「周/日上下拖动改时间」「左缘/右缘分别改开始/结束」「拖中部整体平移」「按整格吸附」。每一轮都因吸附精度、边界判定、回写时机而返工。
2. **甘特视图** —— 维度切换空白、年按钮缺失、水平滚动、今日线粗细对齐，多次修复。
3. **设置面板 / 全局 vs 文件** —— 汇总行位置、标签阈值、月视图任务数等项在「软件设置」与「文件设置」之间反复迁移归类（#287, #288, #346, #366）。
4. **字段显隐 / 字段开关** —— 早期叫「字段设置」，后改「字段开关」，再统一为右侧抽屉式（#85, #88, #93, #97, #108, #109, #117, #118, #122, #161）。
5. **图标** —— 多次通过 `icon-design` 重新检索替换（功能区与视图图标），最终稳定为 Tabler 风格。
6. **构建与校验** —— 几乎每次功能改动都伴随一次构建+校验，是「隐性高频」成本。

## 四、困难点详解

### 1. 日历/甘特的时间-坐标换算
- **难点**：屏幕像素 ↔ 日期时间 不是线性关系（月视图按格、周/日视图按 15 分钟吸附、甘特按维度跨度）。
- **反复原因**：吸附粒度变化（整天 / 15 分钟 / 按周 7 天）、边缘 8px 判定、松手时「整格对齐」与「实时跟随光标」的体验权衡。
- **经验**：把「坐标→时间」与「时间→坐标」抽成纯函数单测；拖拽中只更新临时预览，松手再回写数据源，避免中途多次写 Excel 造成抖动。

### 2. WebView2 生命周期与截图
- **难点**：`CapturePreviewAsync` 只能整页截图，且返回的是 WebView 客户端尺寸的位图；要裁剪「图表内容区」必须用 `_webView.ClientSize` 做比例映射。
- **经验**：JS 侧用 `getBoundingClientRect()` 取视口坐标 → 传 `{x,y,w,h}` 给 C# → C# 按比例映射到 Bitmap 像素 → `Bitmap.Clone(Rectangle,...)`。底部以内容内部首个子元素 `bottom` 为基准，裁掉下方空白。

### 3. 无第三方 PDF 库的手写生成（#376 已移除）
- **难点**：必须是合法 PDF（Catalog/Pages/Page/XObject Image + Contents），图像用 DeviceRGB + FlateDecode(Predictor 15)，zlib 由 `System.IO.Compression.ZLibStream` 生成。
- **坑**：透明像素在 PDF 查看器里变黑 → 先铺白底转 24bit RGB；坐标 1px=1pt；xref 偏移必须精确。
- **经验**：用最小的「一页一图」结构，避免字体/文本流复杂度；先 `bmp.Save` 为 PNG 自检图像正确，再套 PDF 外壳。
- **现状**：#376 依需求移除该 PDF 导出功能（位图为栅格、非矢量，不满足矢量要求）；导出仅保留图片(PNG)与剪贴板。手写 PDF 经验仍保留，供将来若需矢量再实现时复用。

### 4. 构建 ≠ 交付（最隐蔽的坑）
- **难点**：`dotnet build` 只到 `bin/Release/net8.0-windows/`；安装从 `dist/files/` 取。**只 build 不重拷 dist，重装仍加载旧资源**。
- **坑**：覆盖 `dist/files/MultiTableAddin.dll` 时若被 Excel 占用 → `cp` 报 `Permission denied` → 需先 `rm -f` 再 `cp`。
- **经验**：固定两步流水线，并在 `verify-build.py` 比对 dist DLL 时间戳/字节数，确认确实更新。

### 5. verify-build.py 的 UTF-16LE / UTF-8 双编码
- **难点**：DLL 中 C# 字符串字面量是 **UTF-16LE**，内嵌 HTML/JS 是 **UTF-8**；注释和源码片段**不进 DLL**。
- **坑**：用错编码搜索 → 校验 FAIL；把注释当校验串 → 永远找不到。
- **经验**：C# 文本用 `utf-16le` 搜索，JS/HTML 用 `utf-8`；校验串只取真实出现的字符串字面量；每次改 `index.html` 必同步校验串。

### 6. WPF / WinForms 类型歧义
- **难点**：同时 `UseWindowsForms`+`UseWPF`，`Rectangle`/`Color` 解析到 WPF 类型，编译报 CS1729/CS1503。
- **经验**：导出裁剪代码一律用 `System.Drawing.Rectangle`、`System.Drawing.Color.White`、`System.Drawing.Imaging.*` 全限定名。

## 五、修改耗时规律

- **一次改对的功能**：纯文案、纯常量、删除未启用控件——几乎零返工。
- **2–3 轮收敛**：样式对齐、设置项迁移、字段显隐——因「漏改读取处 / 漏同步校验串」返工。
- **5+ 轮拉锯**：日历拖拽、甘特维度、导出裁剪——因交互细节与边界条件不断被发现。
- **每次必做的隐性工作**：构建+拷贝+校验（约 1–2 分钟，但漏一步就全盘「改了没生效」）。

## 六、经验总结（可迁移方法论）

1. **「改了没生效」第一怀疑构建链路**：先确认 dist DLL 时间戳/字节数变了，再怀疑代码。
2. **校验串与代码同源更新**：任何 `index.html` 改动，立刻同步 `verify-build.py` 检查串（正向 + 负向），把「是否真的落地」变成可自动化验证。
3. **拖拽/坐标类需求先写纯函数**：坐标↔时间的换算抽成无副作用函数，前端只改预览、松手才回写，避免抖动与多次写源。
4. **平台耦合代码全限定命名**：混用 WPF/WinForms 时，绘图相关类型一律写全命名空间。
5. **无库约束下的最小实现**：图像等优先手写最小可用结构并自检；PDF 曾手写最小结构（#376 已移除，因栅格非矢量），其经验（FlateDecode + Predictor 15 + zlib）仍保留供复用。
6. **设置项「三处必查」**：默认值、`save*`，、读取处——任何设置迁移都要同时核对这三处。
7. **图标走统一来源**：视图图标固定 Tabler 风格、功能区用单一 PNG、窗口用多尺寸 ICO，避免风格漂移（见《图标信息对照表》）。
8. **文档与代码同步**：功能/兼容性/版本变动时，同步更新《多维表插件使用帮助》《软件设置与文件设置对照表》《项目开发记录》，避免文档滞后于实现。
